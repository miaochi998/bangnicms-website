灾难总会发生——硬盘损坏、勒索软件、人为误操作、机房失火。**有备份 = 能恢复**。

## 灾难类型与应对

### 1. 单条数据误删

**场景**：运营手抖删了关键产品。

**恢复**：

<Steps>

1. 进**用户管理 → 操作日志**

2. 找到该删除操作

3. 看变更前数据

4. 手工**重新录入**

</Steps>

**RTO**：分钟级。

详见 [角色与权限 - 操作日志](/docs/users/roles-permissions#操作日志)。

### 2. 大量数据误删 / 误改

**场景**：某员工误用批量操作删了一类产品。

**恢复**：

<Steps>

1. **立刻冻结写操作**（让运维临时关闭后台）

2. **从最近备份恢复整个数据表**

3. **保留备份后**新产生的数据（人工合并）

4. **验证**

5. **追责**：看操作日志确认是谁

</Steps>

**RTO**：1-4 小时。

### 3. 整个数据库损坏

**场景**：服务器崩溃 / 磁盘故障 / 数据库文件损坏。

**恢复**：

<Steps>

1. **修复硬件**（让运维换硬盘 / 换服务器）

2. **重装 BangNiCMS**（系统代码）

3. **从备份恢复数据库**：

   - 选最近的完整备份
   - 应用之后所有的增量备份

4. **从备份恢复媒体目录**

5. **重启服务**

6. **健康检查**

7. **验证**：抽样、登录、提交测试询盘

</Steps>

**RTO**：4-12 小时。

**RPO**：取决于备份频率（每天备份 → 最多丢 24h 数据）。

### 4. 勒索软件

**场景**：黑客加密了所有数据 + 备份，要求赎金。

**恢复**：

<Steps>

1. **不要支付赎金**（黑名单条款 + 无保证恢复）

2. **断网**：让运维隔离受感染服务器

3. **取证**：保留服务器状态供调查

4. **重建**：

   - 全新服务器（不连旧服务器，避免感染）
   - 装最新 BangNiCMS
   - **从异地备份**恢复（前提：异地备份没被加密）

5. **审计**：找到入侵途径并修复

6. **通知**：相关方 + 监管（如适用）

7. **加固**：详见 [安全最佳实践](/docs/users/security-best-practices)

</Steps>

**RTO**：1-3 天（极复杂）。

**预防**：

- 备份**异地** + **离线**（防勒索软件加密）
- 强密码 + 2FA
- 定期更新系统补丁
- 限制后台访问 IP

### 5. 机房整体灾难

**场景**：火灾、洪水、断电断网。

**恢复**：

<Steps>

1. **切换到异地备用服务器**（如果有）

2. **从异地备份恢复**

3. **更新 DNS**指向新服务器

4. **等待 DNS 传播**（5 分钟-24h）

5. **服务恢复**

</Steps>

**RTO**：

- 有热备服务器：30 分钟-2 小时
- 无热备：4-24 小时

**预防**：

- **3-2-1 备份**（详见 [备份策略](/docs/upgrade/backup#3-2-1-备份原则)）
- 异地热备服务器
- 多 CDN

### 6. DDoS 攻击

**场景**：大量恶意流量让服务无法响应。

**恢复**：

<Steps>

1. **启用 Cloudflare / 阿里云高防**：让攻击流量在防护层被拦

2. **限制 IP 频率**：单 IP 限请求

3. **临时关闭**重资源接口（如登录）

4. **等待攻击者放弃**或被高防过滤

</Steps>

**预防**：

- 始终启用 CDN / WAF
- 反向代理层限流
- 监控异常流量

### 7. 升级失败

详见 [升级流程 - 升级失败的应急](/docs/upgrade/checklist#升级失败的应急)。

### 8. 人为恶意（员工捣乱 / 离职报复）

**场景**：员工删数据 / 改密 / 偷数据。

**恢复**：

<Steps>

1. **立即禁用**该员工账号

2. **强制全员改密 + 启用 2FA**

3. **审计操作日志**：找出所有恶意操作

4. **从备份恢复**被破坏的数据

5. **追责**：法律渠道（如严重）

</Steps>

**预防**：

- 离职即禁用账号（详见 [安全最佳实践 - 离职流程](/docs/users/security-best-practices#离职流程)）
- 强制 2FA
- 操作日志监控

## RTO 与 RPO 评估

定期问自己：

- **RTO**：业务能容忍**多久**不可用？
- **RPO**：业务能容忍**丢失多少**数据？

**典型业务的目标**：

| 业务 | RTO | RPO | 方案成本 |
|---|---|---|---|
| 个人博客 | 24h | 24h | 极低（每日备份） |
| 中小 B2B | 4h | 1h | 中（每日备份 + 异地） |
| 大型电商 | 30 分钟 | 5 分钟 | 高（热备 + 实时复制） |
| 金融 | 5 分钟 | 0 | 极高（多活 + 同步） |

**目标越严 = 成本越高**——根据**业务真实需求**定。

## 灾难恢复演练

**最重要的一步**——很多团队备份从未演练。

**每季度**：

<Steps>

1. **预设场景**（如"假设数据库整库丢失"）

2. **运维操作**：

   - 从备份恢复到测试环境
   - 测量恢复时长
   - 验证完整性

3. **总结**：

   - 实际 RTO 是多少？
   - RPO 是多少？
   - 哪些步骤可以加快？
   - 哪些备份是错误 / 损坏的？

4. **改进**

</Steps>

## 沟通模板

**遭遇灾难时**：

```
紧急通知：

由于 [灾难原因]，邦你科技网站当前不可访问。
我们正在紧急恢复，预计 [时间] 恢复服务。

紧急联系：xxx@example.com / +86 138...

我们对您可能造成的不便深表歉意。
```

**关键**：

- **诚实**：别遮掩问题严重性
- **频繁更新**：每 1-2h 一次
- **道歉 + 行动**：解决问题最重要

## 灾难后的复盘

**事后必做**：

1. **复盘会议**：所有相关人员参加
2. **时间线**：什么时候发生 / 发现 / 响应 / 恢复
3. **根本原因**：为什么发生
4. **改进措施**：未来如何避免 / 减轻
5. **执行**：确保改进真正落地

**目标**：**同样的灾难不要发生第二次**。

## 灾难恢复检查清单

定期评估：

- [ ] 备份完整 + 验证 + 异地
- [ ] 灾难恢复方案文档化
- [ ] 关键人员**知道**怎么操作
- [ ] **演练**过至少一次
- [ ] **RTO / RPO** 符合业务要求
- [ ] **联系方式**最新（云服务商、安全顾问、法律顾问）
- [ ] **保险**（如适用）
