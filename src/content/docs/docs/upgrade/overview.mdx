「备份」是数据安全的最后一道防线，「升级」是获取新功能 + 安全补丁的常规动作。本节给全景。

后台入口：**系统 → 备份与升级**

<Screenshot caption="后台「备份与升级」管理页" hint="顶部状态卡片（最近备份时间 / 当前版本）+ 备份列表 + 升级历史" />

## 为什么备份是关键

**没备份的灾难**：

- 数据库被勒索软件加密 → 整站数据**永远丢**
- 服务器硬盘损坏 → 所有内容 / 媒体丢失
- 误操作删了关键数据 → 没法回滚
- 升级失败 → 没法恢复到旧版

**有备份**：

- 任何灾难都能**恢复到 24h 前的状态**
- 升级失败可**回滚**
- 误操作可**单条恢复**

## 备份的两个层面

### 数据库备份

**包含**：

- 所有内容（产品 / 文章 / 页面 / 下载）
- 所有翻译
- 所有用户 + 操作日志
- 站点设置
- 模型包定义 + 字段值

**不包含**：

- 上传的图片 / 文件（在文件系统）
- 主题 / 插件代码（在文件系统）

### 文件系统备份

**包含**：

- 上传的媒体（图片、视频、PDF）
- 主题 / 插件 / 模型包的 zip 包
- 系统配置文件

**不包含**：

- BangNiCMS 系统代码（重新部署即可）

**两个层面都要备份**——只备数据库 = 恢复时图片全没。

## 升级类型

| 升级 | 频率 | 风险 |
|---|---|---|
| **补丁版本**（X.Y.**Z**） | 每周 | 极低（修 bug） |
| **次版本**（X.**Y**.0） | 每季度 | 低（新功能） |
| **主版本**（**X**.0.0） | 每年 | 中（重大变更） |

详见 [升级流程](/docs/upgrade/upgrade-process)。

## 谁负责备份与升级

| 任务 | 谁做 |
|---|---|
| **设计备份策略** | 运维 + 安全管理员 |
| **执行 / 监控备份** | 运维（自动化） |
| **决定何时升级** | 运营 + 运维 + 总监 |
| **执行升级** | 运维 |
| **测试升级** | 运维 + 业务方 |
| **灾难时恢复** | 运维（紧急） |

**运营**通常不直接操作——但**必须知道**这些事在发生 + 在出问题时能配合。

## 关键时间点

**前期一次性**：

- 部署后**第一周**：配好自动备份 + 测试一次恢复

**日常**：

- **每天**自动备份（运维自动化）
- **每周**抽检最近备份是否完整
- **每月**做一次"假想恢复"演练

**升级时**：

- **升级前 24h**：手动做一次完整备份
- **升级当天**：再备一次
- **升级后**：抽样检查数据完整

## 常见问题

### BangNiCMS 自带备份功能吗？

**自带基础备份**——后台「备份与升级」可以触发数据库备份。

但**完整方案**（异地存储、加密、定时）通常需要运维结合云存储 + 脚本。

### 我能从云端（如 阿里云 / AWS）一键还原吗？

**取决于运维如何部署**：

- 云数据库（RDS）通常支持**任意时间点恢复**（PITR）—— 极强能力
- 自建服务器需要运维写脚本

详见 [备份策略](/docs/upgrade/backup)。

### 升级会破坏数据吗？

**正确升级流程不会** —— BangNiCMS 自带数据迁移，升级时自动转换 schema。

**风险来自**：

- 跨大版本（如 1.x → 3.x）—— 建议**逐版本升级**
- 测试环境没充分验证就上生产
- 升级中网络中断

详见 [升级流程](/docs/upgrade/upgrade-process)。

### 我能跳过升级一直用旧版吗？

可以——但**安全风险增加**：

- 错过安全补丁
- 主题 / 插件可能依赖新版 API
- 长期不升级最后跨多版升级 = 灾难

**建议**：每季度评估一次升级。
